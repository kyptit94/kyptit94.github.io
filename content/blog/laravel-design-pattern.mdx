Laravel is more than just a framework — it's a **collection of well-implemented design patterns**. Understanding these patterns helps you write cleaner code, solve common problems efficiently, and ace technical interviews.

In this post, we’ll cover several **key design patterns** used in Laravel:

- Singleton Pattern
- Factory Pattern
- Repository Pattern
- Strategy Pattern
- Dependency Injection (DI)

We’ll also provide real-world Laravel examples and when to use each pattern.

---

## 🧠 What Are Design Patterns?

Design patterns are **standard solutions** to common software design problems. They’re not code you copy-paste — they’re **guidelines** that help structure your logic better.

---

## 1. 🔁 Singleton Pattern

**Problem it solves:** Ensures a class has only one instance and provides a global point of access.

### 📦 Example in Laravel: The Service Container

Laravel’s **service container** is a real-world implementation of the Singleton pattern.

```php
$this->app->singleton(PaymentGateway::class, function () {
    return new StripePaymentGateway();
});
```

No matter how many times you resolve `PaymentGateway`, Laravel gives you the **same instance**.

### ✅ Use it when:
- You want to avoid recreating the same object multiple times (e.g., config services, caching, logging).

---

## 2. 🏭 Factory Pattern

**Problem it solves:** Centralizes object creation logic.

### 📦 Example in Laravel: Model Factories

Laravel uses the Factory pattern for generating models in testing and seeding.

```php
User::factory()->create([
    'email' => 'test@example.com',
]);
```

Behind the scenes, Laravel creates a user object with random (or specified) attributes.

### ✅ Use it when:
- You want a standard way to create objects, especially in testing or fake data generation.

---

## 3. 🗃 Repository Pattern

**Problem it solves:** Abstracts the data layer from the business logic.

Instead of accessing Eloquent directly in controllers:

```php
$users = User::all();
```

You can abstract it:

```php
interface UserRepositoryInterface {
    public function all();
}

class UserRepository implements UserRepositoryInterface {
    public function all() {
        return User::all();
    }
}
```

Then inject the repository into your controller:

```php
public function __construct(UserRepositoryInterface $users)
{
    $this->users = $users;
}
```

### ✅ Use it when:
- You want better testability, scalability, and separation of concerns.
- You’re working in large applications with complex data access logic.

---

## 4. 🧩 Strategy Pattern

**Problem it solves:** Allows selecting algorithms at runtime.

### 📦 Example in Laravel: Payment Strategies

Imagine a checkout process where users can pay with PayPal, Stripe, or Cash.

```php
interface PaymentMethod {
    public function pay($amount);
}

class PayPalPayment implements PaymentMethod {
    public function pay($amount) {
        // PayPal logic
    }
}

class StripePayment implements PaymentMethod {
    public function pay($amount) {
        // Stripe logic
    }
}
```

Then you choose the payment method dynamically:

```php
public function checkout(PaymentMethod $payment)
{
    $payment->pay(100);
}
```

### ✅ Use it when:
- You need multiple interchangeable behaviors (payment, notifications, file storage, etc.).

---

## 5. 🔗 Dependency Injection (DI)

**Problem it solves:** Removes tight coupling by injecting dependencies from the outside.

Laravel handles DI through the **Service Container**, automatically injecting dependencies when you type-hint them in constructors:

```php
public function __construct(InvoiceService $invoice)
{
    $this->invoice = $invoice;
}
```

Laravel will automatically resolve `InvoiceService` for you.

### ✅ Use it when:
- You want better testing, flexibility, and clean architecture.
- You need to swap implementations (e.g. Fake vs Real service).
